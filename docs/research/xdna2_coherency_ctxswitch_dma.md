# XDNA2 (Strix) via XRT + amdxdna + mlir-aie/IRON: research report

Tags: [DOC] documented / read in source, [INF] my inference, [MEAS] measured by me.
Driver sources were fetched from GitHub amd/xdna-driver main (copies in scratchpad/drv/). Installed here: xrt 2.21.75, xrt-plugin-amdxdna 2.21.75-2, so HEAD may differ in detail from what you run.
Base URL: https://github.com/amd/xdna-driver/blob/main/ (D = drivers/accel/amdxdna/, S = src/shim/)

## 1. Host memory coherency

Facts
- [DOC] The NPU is NOT cache coherent with the CPU. Driver comment above the sync ioctl: "This is required because NPU is not cache coherent device. CPU cache flushing/invalidation is expensive so it is best to handle this outside of the command submission path." (D/amdxdna_gem.c ~L1530)
- [DOC] On PCIe Strix, normal BOs (SHARE/CMD) are drm_gem_shmem pages, mapped to the CPU as ordinary cacheable write-back memory: `shmem->map_wc = false;` (D/amdxdna_gem.c:1050, amdxdna_gem_create_shmem_object). There is no uncached/WC variant for these BOs.
- [DOC] Cache maintenance in amdxdna_flush_bo (D/amdxdna_gem.c:1494-1531) is drm_clflush_virt_range/sg/pages, i.e. CLFLUSH. CLFLUSH writes back a dirty line AND evicts it. It cannot do "write-back only" or "invalidate only". It returns 0 early only for CMA BOs ("CMA create-BOs are coherent (dma_alloc_coherent); no cache maintenance"), and CMA is used only for the platform/NPU3A build (amdxdna_use_cma, D/amdxdna_cma_buf.h:17-23), not for Strix PCIe.
- [DOC] Current shim does the flush in user space on x86: pdev::cache_sync -> clflush_data (mfence; clflush per line; mfence) over bo.vaddr()+offset,size (S/pcidev.cpp:249-313). pdev_kmq::sync_bo always calls cache_sync with the comment "x86 NPU: the DMA layer may mislabel the device as coherent, so it always needs cache maintenance" (S/kmq/pcidev.cpp:44-52). Only aarch64 goes through the SYNC_BO ioctl. Older shims called the ioctl, which ends in the same drm_clflush.
- [DOC] TO_DEVICE and FROM_DEVICE are the same operation on x86: flush+evict of the range. The direction is ignored by amdxdna_flush_bo. The only extra effect of FROM_DEVICE is a debug-BO refresh (D/amdxdna_gem.c:1603-1608).
- [DOC] Flags: I found no flag-dependent sync behaviour for Strix. xrt_bo.h says "cacheable: Only effective on embedded platforms" (/usr/include/xrt/xrt_bo.h:110-111). host_only, cacheable and normal all end up as AMDXDNA_BO_SHARE (or CMD for instruction/ctrl BOs) in the shim (S/buffer.cpp:140-154). Treat all as cached WB memory that needs the same flushes. [INF] for the exact flag mapping; the code that maps flags to BO type is at buffer.cpp:140-154 and I read it only briefly.
- [DOC] The shim itself documents your exact failure. When a BO is expanded/allocated it flushes: "Newly allocated buffer may contain dirty pages. If used as output buffer, the data in cacheline will be flushed onto memory and pollute the output from device. We perform a cache flush right after the BO is allocated" (S/buffer.cpp:~419-424).

Mechanism of your corruption [INF, consistent with the above]
1. CPU memset() leaves the data as dirty lines in L1/L2/L3. DDR still holds old data.
2. The NPU writes its result to DDR through the IOMMU and does not snoop or invalidate those CPU lines.
3. Later the CPU either (a) evicts the still-dirty memset lines, which write back over the NPU result (partial corruption, timing dependent), or (b) reads lines that are still valid in cache and gets stale pre-NPU data. sync(TO_DEVICE) right after the memset writes the memset data to DDR and evicts the lines, so nothing dirty is left to clobber the NPU's output, and later CPU reads miss and fetch the NPU data from DDR.
- Note: sync(FROM_DEVICE) does a clflush, which WRITES BACK dirty lines before evicting. If a line is dirty at that moment, the flush overwrites the NPU's data in DDR. That is why FROM_DEVICE alone cannot repair an output buffer that was dirtied before the NPU ran.

Rules
(a) NPU input buffers written by the CPU: write, then sync(TO_DEVICE) on the written range, before the run is submitted. A run submission does not flush anything for you (the driver says flushing is "outside of the command submission path"). Writes through a numpy view are invisible to any runtime bookkeeping; see amd/IRON#181 (https://github.com/amd/IRON/issues/181), a stale-input bug caused by exactly this.
(b) NPU output buffers that were CPU-written earlier (recycled, memset, or just reused host memory): make the lines clean/absent BEFORE the NPU writes. Do sync(TO_DEVICE) (writeback+evict) after the last CPU write and before the dispatch. After completion, sync(FROM_DEVICE) (evict) before the CPU reads. Between the pre-flush and the post-flush the CPU must not touch the buffer, including speculative or prefetch reads, which can re-fetch lines. A fresh BO is already safe because the shim flushes at allocation (buffer.cpp ~419).
    - If the output is fully overwritten by the NPU, skip any CPU memset of it; you do not need to zero it.
    - Do not use FROM_DEVICE as the "clean before" step on a dirty buffer; use TO_DEVICE (same operation, but it states the intent).
(c) There is no coherent/uncached host allocation option on Strix PCIe in this driver ([DOC] map_wc=false hardcoded). CMA (coherent, no flush) and carveout exist only for platform/bring-up builds (amdxdna_cbuf.c header comment "platform debug/bringup feature"). Workaround [INF]: mmap'd write-combining/uncached CPU mappings are not exposed; the practical approach is the flush discipline above, flushing only the ranges actually written.

Cost [MEAS]: CLFLUSH loop (mfence+clflush per 64 B+mfence) over a 64 MB buffer on this CPU: 0.7-1.0 ms per 64 MB, about 0.011-0.016 ms/MB (roughly 60-90 GB/s), whether the lines were dirty, clean-cached or absent (the memset of 64 MB mostly spilled out of cache already). So flushing is ~10-20 us per MB. [INF] it is cheaper than a DDR copy; flush only the touched byte range, not the whole BO. Script: scratchpad/cf.c.

## 2. Hardware context switching

Facts
- [DOC] Strix firmware >= 6.12 has the AIE2_TEMPORAL_ONLY feature (D/npu4_regs.c:97, "{ AIE2_TEMPORAL_ONLY, major 6, min_minor 12 }"). With it, aie2_alloc_resource requests EVERY hwctx as `start_cols={0}, ncols=total_col` (D/aie2_ctx.c:622-626). The solver then lets contexts with the same (start,ncols) share one partition (aie2_solver.c allocate_partition ~L238-262). Consequence: an 8-col xclbin and a 6-col xclbin never stay spatially resident side by side on current firmware; all contexts time-share the whole array regardless of how many columns the design uses. Your 6-col design buys you no residency. [INF on firmware behaviour; the driver request is [DOC].]
- [DOC] Limits: `npu_task_max = priv->hwctx_limit` (16) is how many map onto the array at once; amd/mlir-aie#3594 reports up to 32 hw_contexts can exist when temporal_only=1 (https://github.com/Xilinx/mlir-aie/issues/3594).
- [DOC] A firmware time quantum exists: DEFAULT_TIME_QUANTUM 30000 us, pushed with aie2_update_prop_time_quota (D/aie2_pci.c:45,205). Phoronix reports a patch making it configurable (https://phoronix.com/news/AMDXDNA-Hardware-Sched-Quant, fetch was 403, content seen via search snippet only). [INF] The quantum only matters when two contexts both have queued work; with synchronous alternation the switch happens on demand when the next context has a command.
- [DOC] Context priority is sent to firmware only if AIE2_PREEMPT is on (D/aie2_message.c:272-288), values REALTIME/HIGH/NORMAL/LOW, default HIGH. Frame-boundary preemption is a runtime cfg default 0 (D/npu4_regs.c:72,77-78).
- [DOC] What a switch costs: no AMD document gives a number. Closest: a full GEMM design reconfiguration was measured as 3.4 ms (XDNA) and 4.9 ms (XDNA2) in "Striking the Balance: GEMM Performance Optimization Across Generations of Ryzen AI NPUs", Sec. 5.3.2 (https://arxiv.org/pdf/2512.13282; Phoenix and a second mini PC). Reconfiguring only BDs/loop counts was "negligible". Your 2.6 ms is in the same range. mlir-aie#2913 says core ELF data is ~85% of the PDI bytes of a reload and skipping it gave 1.47x on a flash-attention run with load_pdi between iterations (https://github.com/Xilinx/mlir-aie/issues/2913).
- [INF] The cost is firmware loading the target design's PDI (core ELFs, switch/DMA config, lock init) through the array's configuration path plus context bookkeeping. It scales with the PDI size, i.e. with how many cores/tiles have programs, not with the DDR payload. I found no source separating "save" from "restore"; AIE core/memory state is not saved in any sense I could find, only the configuration is reloaded. Treat that split as unknown.

Options
1. Avoid switching: batch all work of design A, then all of design B (what your deferred-dW does). Realistic cost per switch ~2.6 ms [MEAS, yours]. Supported today.
2. One xclbin with the union design (one PDI, runtime-selected behaviour via RTP/params or different runtime sequences). Zero switch cost between ops, but needs a superset kernel. Mechanism for parameters: scratchpad parameters / `aiex.sync_scratchpad_parameters_from_host` exist in the local tree (include/aie/Dialect/AIEX/IR/AIEX.td ~L1290-1313), RTPs. Supported but you must write the superset design (your earlier xdna-superoverlay-probe dir looks like this).
3. Several `aie.device`s in one module + full-ELF flow with `aiex.npu.load_pdi {device_ref=@dev}` inside the runtime sequence (one hw_context, one xrt::elf). The local tree supports this: lib/Dialect/AIEX/Transforms/AIEExpandLoadPdi.cpp, AIEMaterializeRuntimeSequences.cpp, test/npu-xrt/loadpdi/aie.mlir, test/python/npu-xrt/full_elf_42/aie_design.py (IRON `npu_load_pdi`, `aiecc --generate-full-elf --expand-load-pdis`), tracking issue https://github.com/Xilinx/mlir-aie/issues/2605. Cost per PDI switch [INF]: still a PDI load, so expect the same order (about 1-5 ms for big designs), but it removes the host round trip and the context switch/command-queue sync; you submit once. Caveats [DOC]: (i) "The firmware optimizes out repeated load_pdi operations if they refer to the same PDI. To force a reload / device reset, intersperse a load_pdi to a different PDI" (AIEX.td:964-968 `AIE_NpuLoadPdiOp`); (ii) PDI loading resets core and lock state, so call sync_scratchpad_parameters after it (AIEX.td:1301-1303); (iii) full-ELF has open correctness bugs reported: mlir-aie#3656 (stale data; root cause was aliased in-place buffers in the fused runlist, per amd/xdna-driver#1646 closure), mlir-aie#3654 (3rd distinct xclbin hw_context in one process produced garbage when BOs were created between kernel runs; created-upfront worked; closed), mlir-aie#3910 (Windows only). Not yet a drop-in for a hand-written xclbin pipeline like yours.
4. Lightweight reset device without core ELFs (mlir-aie#2913, closed: aiecc support request). This makes the reload ~1.5x+ cheaper where only DMA/lock config changes. Only helps if the same cores/programs stay.
5. IRON fused operator (OperatorSequence/FusedMLIROperator in amd/IRON, runs several ops as one ELF/runlist): amd/IRON#237 (changing the runlist under the same name silently reuses the old ELF) and mlir-aie#3656 show it is young. I did not find a measured switch cost.
- Partition sizing: not available as an option on current firmware (see TEMPORAL_ONLY above). Useful only on older firmware (<6.12), where non-overlapping column ranges can be spatially resident [INF from aie2_solver.c, untested].
- Number of contexts: keep the count low and create BOs before running (mlir-aie#3654 trigger); keep the context pool alive (create_ctx is slow, amd/xdna-driver#629).

## 3. DMA bandwidth limits

- [DOC] Measured by AMD-affiliated authors: "micro-benchmarking ... imitate GEMM transfers from DRAM to NPU array and vice-versa, observing ~15 GB/s and ~50 GB/s for XDNA and XDNA2" effective DRAM BW (arXiv 2512.13282, Sec. 5.2.1; dual-channel DDR5-5600 mini PCs). So ~50 GB/s aggregate is the realistic ceiling for a whole array on XDNA2 in a GEMM-like pattern, far below the 128-256 GB/s of the SoC (HeteroMosaic Table 1 lists the SoC peaks, https://arxiv.org/pdf/2607.12839). Strix Halo has more DRAM BW but I found no NPU-specific measurement for it.
- [DOC] Same paper, Sec. 5.2.2: effective DRAM BW depends strongly on contiguous run length. XDNA with k_mt=k_ct gave 1.27 TOPS and rose to saturation as k_mt grew (longer contiguous L3 reads for A row-major and B column-major). Fig. 6.
- [DOC] Burst length: shim-NOC DMA has a configurable burst; NPU2/AIE2P allows 64, 128, 256, 512 bytes (lib/Dialect/AIE/IR/AIETargetModel.cpp:1602-1606; AIE2 only up to 256). The default 0 is "the maximum available burst length" (AIEOps.td ~L882-883; DMATasks.md:36). So by default you already get 512 B bursts when the access is contiguous enough; strided patterns whose innermost contiguous run is shorter than the burst cannot use it. Innermost stride must be 1 (AIEOps.td:972) and units are 32-bit words in the BD [DOC AIEOps.td:1789]. [INF] 16-byte contiguous runs will be burst-inefficient by up to 4-32x vs 64-512 B runs; make the innermost dimension at least 64 B, ideally >=512 B (4 KB page-friendly), and put reordering in L2 (MemTile) rather than L3 if you need a transpose.
- [DOC, AM020] Shim DMA has 2 MM2S + 2 S2MM channels per shim tile with a 4-entry task queue per channel (as in your memory notes, AM020). I did not re-open AM020 here. Per-channel stream width is 32 bit; [INF] at ~1+ GHz that bounds a channel to a few GB/s (I did not find the published figure, not verified). Aggregate: 8 columns x 2 in-channels, so spread traffic across all columns and both channels, with broadcast/multicast to avoid repeated fetches.
- [DOC] Overlapping BD reconfiguration with transfers matters a lot: non-overlapped BD updates dropped int8-int16 GEMM from 30.77 to 22.21 TOPS (-28%) (arXiv 2512.13282 Sec. 5.3.3).
- BO type: [INF] all BOs are cached shmem pages mapped through the IOMMU; I found no BO-type dependence of NPU DMA bandwidth. Large contiguous allocations and 2 MB hugepages could reduce IOMMU TLB misses, but I found no measurement (see amd/xdna-driver#1399 on xrtBOAllocUserPTR cost scaling with 4K pages, https://github.com/amd/xdna-driver/issues/1399).
- AMD guidance found: programming_guide/section-2/section-2d/DMATasks.md (burst_length, task chains), the GEMM paper above. No official bandwidth table found.

## 4. Dispatch overhead

- [DOC] Driver submission path: by default every single exec buffer is wrapped as a one-command command list (`force_cmdlist = true`, D/aie2_ctx.c:28-30, 501-503); ERT_CMD_CHAIN goes to aie2_cmdlist_multi_execbuf (D/aie2_ctx.c:499). That is the in-kernel batching mechanism.
- [DOC] xrt::runlist (installed: /usr/include/xrt/experimental/xrt_kernel.h:21-45) executes a list of xrt::run objects "atomically in the order they are added" as one submission, which maps to a command chain. Use it to submit N dependent ops with one ioctl and one wait. Caveats: runs in a runlist must belong to the same hw_context; amd/IRON#43 reports a driver/XRT regression with ERT_CMD_STATE_TIMEOUT in runlist execution (closed). mlir-aie fused full-ELF runlist bug: #3656.
- [DOC, user report] mlir-aie#3793: single-shot host wall time was ~400-450 us per dispatch from Python (npu_time), against 2.5 us on-chip compute; fit `total = 343 us + 64 us x N` for persistent loops (https://github.com/Xilinx/mlir-aie/issues/3793). Python and pyxrt overhead are included; the author later reported "I solved it" without details.
- [DOC, anecdote] a hobby project reported ~38 us per dispatch with a persistent hw context and ~14 ms if the xclbin is reloaded in the loop (Stardance page found by search, unverified). I could not find an AMD-published per-command latency for amdxdna. [INF] expect tens of us in C++ for a sync xrt::run start+wait (ioctl, mailbox to firmware, IRQ, wake), more in Python.
- Ways to cut it [INF unless marked]: (1) runlist/chain of ops per submission [DOC]; (2) fewer, bigger ops, with the loop inside the runtime sequence (BD repeat counts) [DOC, DMATasks.md]; (3) keep run objects and BOs alive and just set_arg/start again, don't recreate xrt::run; (4) from C++, not Python; (5) pipeline: submit run N+1 before waiting on N (same context is in-order); (6) QoS priority only reaches firmware when AIE2_PREEMPT is available and defaults to HIGH, so there is little to gain; set REALTIME only for latency under contention [DOC aie2_message.c:272-288]; (7) clock/power: low-priority contexts get lower DPM level and gops/fps/latency hints pick DPM level (aie2_solver.c:118-150), so default (no hints = max DPM level) is already best for throughput; (8) amd/mlir-aie#2236 "Support for fast dynamic dispatch" is an open design item (https://github.com/Xilinx/mlir-aie/issues/2236) with no results.

## Recommended actions
1. Rules for CPU/NPU buffers: sync(TO_DEVICE) of the written range after every CPU write to an input and, for recycled outputs, after the last CPU write and before dispatch; sync(FROM_DEVICE) before CPU reads; never touch outputs in between. Source: S/pcidev.cpp:249-313, S/buffer.cpp:419-424, D/amdxdna_gem.c:1050,1494-1531.
2. Skip CPU zeroing of NPU-fully-written outputs; flush only touched ranges (~15 us/MB [MEAS]).
3. Don't expect two xclbin contexts to stay resident on Strix with current firmware (aie2_ctx.c:622-626, npu4_regs.c:97). Batch by design (already done), or merge into one superset xclbin, or try full-ELF multi-device with load_pdi (needs validation; open bugs #3654/#3656).
4. For throughput: runlist/chain submission and bigger fused ops (aie2_ctx.c:499-503, xrt experimental runlist).
5. For bandwidth: assume ~50 GB/s NPU-wide (arXiv 2512.13282 Sec. 5.2.1), keep contiguous runs >= 64-512 B, leave burst_length at default (512 B on NPU2), overlap BD reconfiguration with transfers, keep <=4 queued tasks per shim channel.
6. Unknowns I could not resolve from sources: exact firmware switch cost breakdown; per-channel GB/s; native dispatch latency in C++ on Strix. These need your own microbenchmark (e.g. NOOP xclbin with and without runlist).
